# 테차 자동화 앱 설계 표준

토큰을 아끼면서 최고 품질을 내는 방법은 단 하나다: **비싼 호출을 줄이는 게 아니라, 불필요한 호출을 없애는 것.**
잘못된 설계로 전체 재생성을 반복하는 것이 가장 큰 토큰 낭비다. 그래서 설계가 먼저다.

---

## 0단계 — 설계 없이는 구현하지 않는다 (필수)

새 자동화 앱 요청을 받으면, 코드 작성 전에 아래 설계표를 먼저 만들어 사용자에게 보여주고 컨펌을 받는다.

| 항목 | 정의할 내용 |
|---|---|
| 단계 분해 | 전체 파이프라인을 단계로 쪼갠다 (예: 입력→생성→컨펌→후속생성→출력) |
| 단계별 I/O | 각 단계의 입력과 출력 형식을 명시한다 (JSON 스키마 수준까지) |
| AI 필요 여부 | 각 단계가 AI 호출이 필요한지, JS 로직으로 충분한지 구분한다 |
| 모델 배정 | AI가 필요한 단계에 아래 '모델 선택 기준'으로 모델을 배정한다 |
| 컨펌 게이트 | 사람이 확정해야 다음 단계로 넘어가는 지점을 정한다 |
| Claude 불가 구간 | 이미지 생성, 영상 렌더링 등 별도 도구가 필요한 구간을 명시한다 |

설계표는 표 또는 다이어그램으로 시각화해서 보여준다. 사용자가 "바로 만들어"라고 명시하지 않는 한, 설계 컨펌 후에 구현을 시작한다.

**기준 파이프라인 (숏폼 영상 자동화):**
주제 입력 → 대본 생성/수정(확정) → 장면별 이미지·컷 추천 → 이미지 소스 확보(촬영/AI생성, Claude 외부) → 자막·BGM → 편집·렌더링(Claude 외부, 스크립트 생성은 가능) → 업로드
새 앱을 설계할 때 이 구조에 매핑해 본다. 대응되는 단계가 있으면 기존 앱(숏폼 대본 빌더, 퍼널데스크)의 출력 형식과 호환되게 만든다.

## 모델 선택 기준

### 실행 환경부터 확인한다
- **Claude.ai 아티팩트 앱(React)**: 모델은 `claude-sonnet-4-6` 고정. 아티팩트 내 API는 이 모델만 사용한다. 모델 티어링이 불가하므로, 토큰 최적화는 아래 '호출 설계'로 해결한다.
- **자체 백엔드 / Claude Code / 외부 스크립트**: 모델 티어링이 가능하다. 아래 기준을 적용한다.

### 티어링 기준 (백엔드/스크립트 빌드 시)
| 작업 성격 | 모델 | 예시 |
|---|---|---|
| 분류, 추출, 짧은 변형, 형식 변환 | Haiku 4.5 | 주제 태깅, 자막 길이 조정, 해시태그 생성 |
| 일반 생성, 구조화된 판단 | Sonnet 4.6 | 대본 초안, 컷 추천, FAQ 생성 |
| 최종 확정 카피, 고난도 종합 | Opus 4.8 | 확정 직전 대본 1회 폴리싱, 전략 문서 |

**하이브리드 패턴이 기본값이다**: 반복 초안은 저렴한 모델로 여러 번 → 사용자 컨펌 직전 상위 모델로 1회 다듬기. Opus는 확정 직전 1회 폴리싱에만 배정한다.
최신 모델명·가격은 변할 수 있으니, 백엔드 빌드 시 docs.claude.com에서 확인 후 확정한다.

## 호출 설계 — 토큰 효율 규칙

1. **부분 재생성 원칙**: 사용자가 한 부분만 불만이면 그 부분만 다시 생성한다. 전체 재생성 버튼과 부분 재생성 버튼을 반드시 분리해서 UI에 넣는다. (예: "이 장면만 다시")
2. **웹검색은 옵트인, 기본값 아님**: 웹검색 도구는 뉴스·시사 등 실시간성이 꼭 필요한 경우에만 켠다. 브랜드 일반 정보(관리법, 상품 특징, 자주 나오는 소재 등)는 검색 없이 처리할 수 있는 주제 뱅크(고정 배열)를 만들어 기본 경로로 두고, 검색이 필요한 경로는 사용자가 명시적으로 선택하게 한다. 검색 호출은 토큰·속도 비용이 가장 큰 단일 요인이므로, 기본 경로는 항상 주제 뱅크 쪽에 둔다.
3. **확정된 결과는 다시 보내지 않는다**: 컨펌 게이트를 통과한 텍스트는 이후 호출에서 요약본만 컨텍스트로 전달한다. 원문 전체를 매번 실어 보내지 않는다.
4. **JSON-only 응답 강제**: 시스템 프롬프트에 "JSON만, 다른 설명 없이"를 명시하고 ```json 펜스 제거 후 파싱한다. 설명 문장은 전부 낭비 토큰이다.
5. **max_tokens 상한을 작업별로 설정**: 짧은 작업(자막 한 줄, 태그)은 200~300, 대본 생성은 1000. 호출별 상한을 표로 먼저 정하고 시작한다.
6. **결과 캐싱**: `window.storage`(아티팩트) 또는 파일(스크립트)에 결과를 저장하고, 동일 입력 재요청 시 저장본을 먼저 보여준다.
7. **일관성이 필요하면 합치고, 독립적이면 나눈다**: 한 호출로 4장면을 한 번에 생성하는 것(1회)과 장면별 4회 호출을 비교해, 함께 생성해야 일관성이 좋은 것은 병합하고(대본), 독립적인 것은 분리한다(장면별 재생성).
8. **AI가 필요 없는 건 JS로**: 글자 수 계산, 시간 배분, 형식 검증, 정렬·필터는 코드로 처리한다.

## 품질 게이트

모든 생성 단계의 시스템 프롬프트에 아래를 포함한다 (퍼널데스크 제외 규칙과 동일):
- 숫자와 출처가 있는 만큼만 말한다 (절대적 표현·검증 불가 수치·조작된 지표 금지)
- 비교는 자사 옵션 간에서만 한다 (경쟁사 실명 비방 금지)
- 마감·재고는 실제 값일 때만 쓴다 (인위적 긴급성 금지)
- 모든 스펙 문장은 "그래서 ~하다"로 끝맺는다 (기능 나열 금지)

컨펌 게이트 규칙:
- 하위 단계 생성 버튼은 상위 단계가 확정된 뒤에 열린다 (대본 확정 후에만 이미지 추천 가능)
- 확정 액션은 시각적으로 구분한다 (확정 = sage 그린 버튼)

## 대중 글쓰기 공통 규칙 (모든 글 생성 앱 필수)

기사·블로그·인스타·스레드 등 **대중에게 공개되는 모든 글**의 시스템 프롬프트에 아래 규칙을 넣는다.
플랫폼 톤(반말/존댓말, 길이)은 앱마다 다르지만, 이 규칙은 톤 위에 항상 적용되는 상위 원칙이다.

**독자를 대하는 태도**
- 옆에서 같이 이야기하는 눈높이로 쓴다. "~해야 합니다", "모르시겠지만" 같은 내려다보는 말투 대신 "저는 이렇게 해요".
- 독자를 이미 알 만큼 아는 사람으로 대한다. 설명은 "혹시 몰라서 덧붙이면" 정도로.
- 독자를 집단이 아니라 한 사람으로 부른다 (성별·연령·지역·직업·외모·소득 일반화·비하 금지).
- 구매 이유는 잃는 것이 아니라 얻는 것으로 말한다 (죄책감·불안·열등감 자극 금지).

**감정과 표현**
- 같은 지적도 독자 편에 서서 쓴다. 읽고 나서 편이 생겼다고 느끼게.
- 부정적 정서로 시작했으면 공감→해소 순서로 닫는다. 마지막 문장은 항상 해소 쪽.
- 담백하게 쓴다. 감정은 형용사가 아니라 장면과 사실로 전한다.
- 강조는 내용으로 한다. 느낌표·이모지는 글 하나에 0~1개.

**정직성**
- 숫자와 출처가 있는 만큼만 말한다 (검증 불가 수치·조작된 지표·거짓 후기 금지).
- 절대적 표현("무조건", "100%", "누구나", "최고") 대신 확인된 사실을 그대로 쓴다.
- 비교는 자사 상품·옵션 간에서만 한다 (경쟁사·타인 실명 비방 금지).
- 마감·재고는 실제 값일 때만 쓴다 (가짜 마감, "오늘만" 금지).
- 인용은 원문이 말한 만큼만 옮긴다. 출처가 불확실하면 확인한 뒤 쓴다.

**가독성**
- 한 문장에 한 메시지. 문장은 60자 안에서 끝낸다.
- 어려운 전문용어는 풀어 쓰거나 짧게 설명한다.
- 클리셰·상투어("바쁘시겠지만", "다름이 아니오라") 최소화.

**자기 점검 한 줄**: "내가 독자라면 이 글을 읽고 기분이 상하거나, 무시당했다고 느끼거나, 속았다고 느낄까?" — 하나라도 걸리면 다시 쓴다.

## 테차 브랜드 표준 (모든 앱 공통)

- 색: 수국 블루 `#6E82A6`(포인트·신뢰), 무드등 앰버 `#EFB054`(CTA), 크림 페이퍼 `#FAF7F1`(배경), 공방 브라운 `#3A322B`(텍스트), 잎사귀 그린 `#7C8B6F`(확정 상태)
- 폰트: Pretendard(본문), Gowun Batang(헤드라인)
- 카테고리: 꽃선물/꽃다발 · 데스크테리어 · 인테리어 소품
- 이미지 자리 포맷: `📷 이미지 자리: [내용 설명]—프롬프트: [영문 생성 프롬프트]` — 모든 앱에서 이 포맷을 통일해 도구 간 복사·이동이 가능하게 한다
- 숏폼 대본 구조: 훅(시선, ~8%) → 공감(문제, ~32%) → 전환(해결, ~42%) → CTA(잔여)
- 스레드 글 스타일 5선(글쓰기 앱에서 사용자가 고르는 톤): ①정보 제공(존댓말·팩트·저장 유도) ②B급 유머(음슴체·자학개그·도파민) ③감성 에세이(다정체·의미·팬덤) ④화두 제시(질문형·댓글 유도, 단 논쟁·공격적 주제는 배제) ⑤날것 비하인드(반말·일기체·실시간 TMI). 스타일은 공통 구조 규칙 위에 얹어 '어조'를 덮어쓴다. 스타일 스펙은 고정 상수로 두고 검색 없이 프롬프트에 주입한다(토큰 절약).

## 아티팩트 구현 표준

- `localStorage`/`sessionStorage` 사용 금지 → `window.storage` API 사용, 모든 호출 try-catch
- 연관 데이터는 하나의 키에 병합 저장 (예: `draft:{id}`에 폼+대본+이미지추천 통째로) — 읽기·쓰기 각 1회로 끝낸다
- HTML `<form>` 태그 금지 → onClick 핸들러 사용
- 자동 저장은 600ms 디바운스, 저장 실패는 조용히 다음 변경 때 재시도
- 초안 목록 사이드바 + 작성자·수정일 표시 (팀 공유 앱이면 shared=true 사용, 사용자에게 공개 범위 고지)
- 에러는 한국어로 친절하게, 원인 포함 표시
