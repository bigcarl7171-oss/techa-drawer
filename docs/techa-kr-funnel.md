# techa.kr 유입·데이터 설계 (1단계)

작성 2026-08-02. 목적은 **판매 전환이 아니라 관계와 데이터 축적**이다.
파는 건 스마트스토어가 하고, techa.kr은 **"챙겨야 할 날"을 알아내는 곳**이다.

---

## 1. 접점별 QR 주소

인쇄물마다 **다른 UTM**을 붙여야 어느 접점이 실제로 작동하는지 알 수 있다.
UTM 없이 뿌리면 3개월 뒤 "태그가 효과 있었나?"에 답할 수 없다.

| 접점 | 주소 | 비고 |
|---|---|---|
| **제품 부착 태그** | `techa.kr/care/?utm_source=tag&utm_medium=product` | 최우선. 제품 수명(3년) 내내 노출됨 |
| 패키지 동봉 카드 | `techa.kr/care/?utm_source=card&utm_medium=package` | 개봉 순간 1회 |
| 스마트스토어 상세페이지 | `techa.kr/care/?utm_source=store&utm_medium=detail` | 구매 전 방문자까지 흡수, 비용 0 |
| 배송 알림톡 | `techa.kr/care/?utm_source=alimtalk&utm_medium=shipping` | 발송 비용 없음 |
| 인스타 프로필 | `techa.kr/care/?utm_source=instagram&utm_medium=bio` | |

### 제품군을 미리 지정하려면

`?p=` 파라미터로 관리법 탭을 열어둔 상태로 보낼 수 있다.
비누꽃 상품에 붙이는 태그라면 비누꽃 탭이 먼저 열리는 편이 친절하다.

```
/care/?p=preserved    프리저브드 (기본값)
/care/?p=soap         비누꽃
/care/?p=silk         실크플라워
/care/?p=succulent    다육이
```

조합 예시 — 비누꽃 제품에 붙일 태그:
```
techa.kr/care/?p=soap&utm_source=tag&utm_medium=product
```

## 2. 수집하는 데이터 (GA4 커스텀 이벤트)

`TECHA.track(name, params)` 로 기록한다. GA4가 꺼져 있거나 광고차단으로 막혀도 조용히 넘어간다.

| 이벤트 | 발생 시점 | 파라미터 | 알 수 있는 것 |
|---|---|---|---|
| `situation_click` | 홈 상황 카드 클릭 | `situation` | **어떤 상황에 수요가 큰가** → 상품 기획 근거 |
| `care_view` | 관리법 탭 조회 | `product` | 어떤 제품이 실제로 선물됐나 |
| `news_signup_click` | 알림받기 유도 클릭 | `situation` | **핵심 전환 지표** (실제 동의 여부는 네이버 쪽이라 클릭까지만 측정됨) |
| `shop_click` | 스마트스토어 이동 | `placement` | 어느 페이지가 실제로 파는가 |
| `contact_click` | `/contact/` 등 문의 페이지로 이동 (2026-08-20 추가) | `placement` | B2B·단체 문의 글이 실제 문의로 이어지는가. `#techa-cta`에 `data-href`를 지정한 글에서만 발생 — `shop_click`(스토어 이동)과 섞이지 않게 별도 이벤트로 분리했다 |

### GA4에서 확인하는 법
보고서 → 참여도 → 이벤트에서 위 4개를 확인한다.
`situation` 같은 파라미터를 쪼개 보려면 **관리 → 맞춤 정의 → 맞춤 측정기준**에
`situation`, `product`, `placement` 를 등록해야 한다(등록 전 데이터는 소급 적용 안 됨).

## 3. 기념일 재구매 — 스마트스토어 '알림받기' 기반 (폼 방식 폐기)

### 왜 방향을 바꿨나

처음엔 `care/` 페이지에서 기념일(이름·날짜·연락처)을 직접 입력받는 폼을 계획했다.
문제가 둘이었다:

1. **신뢰 순서가 거꾸로였다.** QR을 찍는 사람은 선물을 받은 타인이다. 테차와 거래한
   적 없는 사람에게 처음 만난 페이지에서 연락처부터 요구하면 입력률이 0%에 수렴한다.
2. **절반만 자동화였다.** 폼 응답이 표에 쌓이는 것까지는 자동이지만, 그 표를 열어보고
   "이번 달에 누구 챙겨야 하지"를 판단해 메시지를 쓰고 보내는 건 여전히 사람이 매번
   기억해야 하는 일이었다. 5년째 소수 인원으로 운영해온 구조에서 이런 새 루틴은
   결국 안 지켜진다.

### 대신 쓰는 방법: 스마트스토어 알림받기

네이버 스마트스토어에는 고객이 **[알림받기]** 버튼을 눌러 동의하면, 판매자가 그
동의자 전체에게 단체 메시지(네이버 톡톡)를 보낼 수 있는 기능이 이미 있다.

이 방식이 위 두 문제를 동시에 피한다:

- **개인정보를 새로 받지 않는다** — 네이버가 이미 관리하는 동의·연락처를 그대로 쓴다.
- **발송이 개인별이 아니라 세그먼트 단위다** — "작년 이맘때 산 사람 전체"에게 캠페인당
  한 번만 보내면 된다. 연 4회 캠페인이면 사장님이 기억할 일도 연 4번뿐이다.
- **법적으로도 안전하다.** 정보통신망법 제50조는 광고성 정보 발송에 사전 동의를
  요구하는데, 알림받기 버튼을 누르는 행위 자체가 그 동의다. 참고로 거래 종료 후
  6개월 이내는 동의 없이도 광고를 보낼 수 있는 예외가 있지만, 어버이날처럼 작년
  구매자에게 약 12개월 뒤 연락해야 하는 캠페인엔 이 예외가 부족하다. 알림받기는
  기간 제한이 없는 동의라 이 공백을 메운다.
- **사실상 무료다.** 알림받기 고객 + 최근 방문·결제 고객에게는 월 1회 무료 발송이
  가능하다. 그 범위를 넘으면 건당 10원.

### care 페이지에서의 역할

QR로 들어온 낯선 방문자(선물 받은 사람)에게 개인정보를 요구하는 대신, 스마트스토어
알림받기로 안내한다. `care/index.html`의 저장 블록:

```html
<a id="newsSignup" href="https://smartstore.naver.com/itecha" ...>테차 알림받기 →</a>
```

네이버 알림받기 버튼에는 직접 딥링크가 없어서, 스토어 홈으로 보내고 안내 문구로
"좌측 상단의 알림받기를 눌러주세요"라고 알려준다.

### 캠페인 만드는 법 (연 4회, 인프라 없음)

```
① 알림받기 동의자 모으기 (상시)
   배송 완료 알림톡·포장 안내문에 "알림받기 하면 다음 시즌 미리 알려드려요" 문구
   → 쿠폰([고객혜택관리]→[혜택 등록]에서 알림받기 고객 타겟 지정)과 묶으면 동의율 상승

② 세그먼트 확인 (캠페인 2주 전)
   스마트스토어 주문 내역에서 "작년 이맘때 구매한 사람" 기간 필터

③ 메시지 작성·발송 (캠페인당 약 10~20분)
   판매자센터에서 알림받기 고객 대상 톡톡 발송
   톤은 할인이 아니라 "챙겨드립니다" — 할인 프레임을 쓰는 순간 최저가 셀러로 읽힌다

④ 반복 — 어버이날 · 스승의날 · 명절 · 연말(예: 크리스마스)
```

## 4. 홈 상황 카드

현재 4개. `index.html` 의 `.shell-situations` 안에 있다.

| key | 라벨 | 목적지 | 실제로 해주는 일 |
|---|---|---|---|
| `birthday` | 태어난 달의 꽃 | 탄생화·꽃말 | 달 선택 → 꽃말·유래·선물 제안 |
| `parents-day` | 어버이날 | D-Day | 5/8 자동 입력 |
| `teachers-day` | 스승의날 | D-Day | 5/15 자동 입력 |
| `couple` | 100일·1주년 | D-Day | '시작일 포함' 자동 체크 |

### 카드를 추가할 때의 기준

**카드마다 도착지에서 실제로 뭔가가 자동으로 일어나야 한다.**
처음엔 5개였는데 그중 "어머니 생신"과 "집들이·개업"은 날짜를 직접 입력하게 하고
문구만 바뀌었다. 즉 그냥 D-Day 계산기를 누른 것과 화면이 같았다.
카드에 "며칠 남았을까요"라고 써놓고 정작 그 날짜를 모르니 한 번 속이는 셈이라 뺐다.

- 생신은 "며칠 남았나"보다 **"뭘 줄까"** 가 더 맞는 질문이라 탄생화로 보낸다.
- 라벨은 도착지가 실제로 하는 일을 그대로 쓴다. "생신 선물 고르기"(구매 약속)가 아니라
  **"태어난 달의 꽃"**(정보 제공). 탄생화는 선물 아이디어를 *얻는* 곳이지 *사는* 곳이 아니다.
- 집들이·개업은 대응하는 도구가 없어서 뺐다. 나중에 맞는 도구가 생기면 다시 넣는다.

D-Day 쪽 상황 정의는 `ko/dday/index.html` 의 `SITUATIONS` 객체에 있다.
날짜가 고정된 기념일은 올해 날짜가 지났으면 내년으로 넘어가므로,
안내 문구에 "올해" 대신 `{y}` 를 써서 실제 계산된 연도로 치환한다.

**3개월 뒤 할 일**: `situation_click` 데이터를 보고 안 눌리는 카드는 빼고 새 상황을 넣는다.
카드가 많아지면 선택 과부하로 클릭률이 떨어지므로 4~5개를 유지한다.

## 5. 지켜야 할 선

사이트 소개 페이지에 **"설치도 회원가입도 광고성 팝업도 없다"** 고 이미 약속했다.

- 홈에서 상품을 직접 팔지 않는다. 상황 카드는 **도구 진입점**이지 상품 진열이 아니다.
- 상품 제안은 그 날짜를 실제로 계산한 사람에게만, 결과 화면에서 노출한다.
- 관리법 페이지는 **실용 정보를 먼저 주고** 그다음에 기념일 저장을 요청한다.
  받는 사람은 테차에 아무 빚이 없다. 먼저 주지 않으면 요청할 자격이 없다.
